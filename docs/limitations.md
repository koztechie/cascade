# Limitations

Cascade is deliberately small. This page lists what it does not do, so nobody
has to discover it the hard way.

## Data

- **Synthetic catalog.** `store/catalog.rl` is generated by
  `scripts/generate_data.py` (seed 42): realistic structure, deliberate
  defects, no real business data. Pointing Cascade at a real catalog requires
  an importer, which is out of scope for this submission.
- **No live integrations.** No connection to Merchant Center, Rozetka, Prom.ua
  or any CRM. The graph models the *shape* of those systems, not their APIs.
- **One store, one process.** Like Relate itself: no multi-tenant access, no
  concurrent writers across processes.

## Queries

- **Fixed scenarios.** The four demo queries are the product. Arbitrary
  natural-language questions are not answered without an agent layer on top
  (an MCP endpoint is provided; see below).
- **Fixed depth.** Blast radius traverses up to 4 hops; deeper impact exists in
  theory but is cut from scope on purpose (clarity over exhaustiveness).
- **No time travel.** The graph is current-state. Historical change log is not
  modeled.

## Product gaps (honest list)

- Vector/embedding retrieval is **not** wired in this version; search is by
  exact match and traversal only.
- The MCP endpoint is read-only in the documented setup.
- No auth: Relate has no users/roles by design; file permissions are the
  boundary.

## What would come next

An importer for real catalogs (CSV/API), a change log with temporal queries,
write-mode MCP for proposing changes, and vector retrieval for
"find the change ticket, then traverse its blast radius".

## One writer per store (Relate's rule)

Relate allows a **single writer per store**. Stop `relate serve` (or any other
process holding `store/catalog.rl`) before `make store`, `make demo` or
`make report` — they rebuild or reopen the file. Concurrent readers are fine;
concurrent writers are not. This is a property of Relate itself, not of
Cascade.

## The graph, not the model, is the source of truth

Cascade has no LLM in its answer path: every number comes from Cypher against
`store/catalog.rl`. An agent may *choose* the query, but it cannot rewrite the
result — each claim in `docs/agent-session.md` is replayable by pasting the
printed statement, `make verify` asserts the pack's outputs, and a
parameter-injection test proves values stay values. If a model and the graph
ever disagree, the graph wins.

## Availability is not review state

Fixing a field and getting re-approved are two different states. Filling the
missing `gtin` clears the *risk pool* (query `05`/`07`), but listings that were
already rejected stay rejected until they are re-submitted — listing status and
feed contract live independently, exactly like "a source is available again but
the earlier review is still invalid". Cascade never silently promotes a fix
into an approval.
